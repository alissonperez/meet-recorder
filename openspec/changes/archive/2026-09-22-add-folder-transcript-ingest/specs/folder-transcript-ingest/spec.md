## ADDED Requirements

### Requirement: Opt-in folder-ingest configuration
The system SHALL read an optional `folder_ingest` configuration section
from `~/.config/meet-recorder/config.yaml` consisting of `enabled`,
`directories` (a list of filesystem paths), `poll_interval_minutes`, and
`max_attempts`, and SHALL treat the feature as disabled when the section is
absent, `enabled` is false, or `directories` is empty, without affecting
existing behavior.

#### Scenario: Feature configured and enabled
- **WHEN** `config.yaml` contains a `folder_ingest` section with
  `enabled: true` and at least one entry in `directories`
- **THEN** the periodic poller is eligible to run and the CLI ingestion
  command scans every configured directory

#### Scenario: Feature absent, disabled, or unconfigured
- **WHEN** `config.yaml` has no `folder_ingest` section, has
  `enabled: false`, or has an empty `directories` list
- **THEN** the config still loads and validates, the periodic poller is a
  no-op, and unrelated behavior is unchanged

### Requirement: Directory scan, root level only
The system SHALL, for each configured directory, scan only its top level
(not subdirectories) for regular files whose extension is `.txt` or `.md`
(case-insensitive), and SHALL process the matched files in a deterministic
order.

#### Scenario: Matching files picked up
- **WHEN** a configured directory's top level contains `.txt` and `.md`
  files
- **THEN** each is treated as a candidate for ingestion

#### Scenario: Non-matching files and subdirectories ignored
- **WHEN** a configured directory's top level contains files with other
  extensions, or subdirectories (including the app's own `processed/` and
  `failed/`)
- **THEN** none of them are scanned or treated as candidates

#### Scenario: Missing or unreadable directory does not abort the run
- **WHEN** a configured directory does not exist or cannot be listed
- **THEN** a warning is logged, that directory is skipped for the current
  scan, and scanning continues for the other configured directories

### Requirement: Standard-pipe processing of picked-up files
The system SHALL, for each candidate file not currently skipped by ledger
state, read its text content and run it through the same summary/title/
output pipeline used for a standalone transcript ingestion, using the
file's modification time as the output timestamp and an LLM-generated
title, and SHALL write a transcript Markdown file and a summary Markdown
file using the existing transcription output layout.

#### Scenario: File processed into transcript and summary
- **WHEN** a candidate file is read successfully
- **THEN** a transcript Markdown file and a summary Markdown file are
  written using the existing per-month-directory, event-based filename
  layout, with the file's modification time as the timestamp

#### Scenario: Title is always LLM-generated
- **WHEN** a candidate file is processed
- **THEN** its output title is generated by the title model from the
  generated summary, since no calendar event or explicit title is
  available for a folder-ingested file

### Requirement: Move-based dedup on success
The system SHALL, immediately after a candidate file is successfully
processed, move it out of the watched directory's top level into a
`processed/` subdirectory of that same directory, so a later scan of that
directory never processes it again. If the destination path already
exists, the system SHALL append a disambiguating numeric suffix rather than
overwrite the existing file or leave the source file unmoved.

#### Scenario: Processed file moved out of the watched root
- **WHEN** a candidate file is successfully processed
- **THEN** it is moved into a `processed/` subdirectory created inside the
  directory it was found in, and is not seen as a candidate on any later
  scan

#### Scenario: Destination name collision is disambiguated
- **WHEN** a file is successfully processed and a file with the same name
  already exists in the destination `processed/` (or `failed/`)
  subdirectory
- **THEN** the moved file is renamed with a numeric suffix so both files
  are preserved

### Requirement: Bounded retry and give-up on failure
The system SHALL, when processing a candidate file fails for any reason
(unreadable/non-text content, or a failure anywhere in the standard
pipeline), record the failure in a persistent retry ledger keyed by the
file's absolute path, retry it no more often than once per hour regardless
of the configured poll interval, and, once the configured `max_attempts`
is reached, move the file into a `failed/` subdirectory of the directory it
was found in and stop retrying it.

#### Scenario: Failed file retried on a throttled schedule
- **WHEN** processing a candidate file fails and its retry budget is not
  yet exhausted
- **THEN** the file is left in place, its ledger entry's attempt count is
  incremented, and it is not retried again until at least one hour has
  elapsed, even if the poll interval is shorter

#### Scenario: Exhausted retry budget moves the file to failed/
- **WHEN** a failing file's attempt count reaches the configured
  `max_attempts`
- **THEN** the file is moved into a `failed/` subdirectory created inside
  the directory it was found in, and is not retried again

#### Scenario: Successful file never reaches the ledger
- **WHEN** a candidate file is processed successfully on its first attempt
- **THEN** no entry is written to the retry ledger for it

### Requirement: On-demand CLI ingestion
The system SHALL provide a CLI command that scans every configured
directory and processes eligible files once, independent of the menu bar
app.

#### Scenario: Running folder ingestion from the CLI
- **WHEN** the user runs the folder-ingestion command
- **THEN** every configured directory is scanned once, eligible files are
  processed, written files are logged, and a run that finds nothing to
  process reports that plainly and exits successfully
